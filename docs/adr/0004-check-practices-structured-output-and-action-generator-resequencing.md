# check_practices ships as structured JSON + --fix; Root/Member Action generators pulled forward, ATOM/App template and Collection Action deferred

ADR 0002 scoped `thecore:check_practices` to Phase 1 (alongside the Model/Migration generator hook) but it was never built — Phase 1 shipped without it. Resuming this work, `check_practices` is built now, paired with the Root/Member Action generators that ADR 0002 originally grouped into Phase 2 (alongside the ATOM generator and the App application template). The pairing follows from the domain, not just convenience: `checkPractices.js`'s own violations (missing companion view/JS/scss, missing `after_initialize.rb` require line, missing locale entries) are literally the inverse of what a Root/Member Action generator produces. Building the generator first gives `check_practices` a canonical "correct shape" to check against, and each Fixable Violation's fix can delegate straight to the generator's own file-creation step instead of re-implementing template rendering inside the rake task.

The ATOM generator and the App application template stay deferred to a later session: they're structurally unrelated to the Action Companion surface (the ATOM generator itself shells out to `rails plugin new` plus gemspec/CI scaffolding; the App template is a `rails new -m` script, not a generator at all), so pulling them in now would dilute this pass without sharing any of its groundwork.

Collection Action — the third action type ADR 0002's phrasing names ("Root/Member/Collection Action scaffolding") — is explicitly **not** built alongside Root/Member here: it has no existing implementation in `thecore_code_extension` to port (no `addCollectionAction.js`), and RailsAdmin's collection actions are bound to multiple selected records rather than zero-or-one, which is a genuinely different design problem, not a mechanical port of Root/Member's shape. It remains a named, tracked gap for a future addition. `check_practices` nonetheless scans `lib/collection_actions/` (which `createATOM.js` already creates in every ATOM) with the same generic action-file rules used for Root/Member — marker checks, companion view/JS/scss, locale entries, the `after_initialize.rb` require line — since a hand-written collection action already sitting in that directory today, with no generator to have gotten it right, is exactly where a silent, unreported breakage is most likely.

`check_practices` emits structured JSON — one entry per Violation (`file`, `line`, `message`, `severity`, `fixable`, and a stable `code` such as `missing_companion_view`/`orphan_api_include` that a future consumer can filter on without depending on the human-readable `message` text) — instead of plain text, and accepts a `--fix` flag that applies every fixable violation in one pass (mirroring `checkPractices.js`'s existing single Yes/No "fix N of M?" prompt, not per-violation selection). `thecore_code_extension`'s `checkPractices.js` becomes a thin wrapper: shell out to `rails thecore:check_practices --json`, render the parsed result as VS Code diagnostics, and — on confirmation via the same QuickPick — re-invoke with `--fix`. This is the same delegation pattern `addModel`/`addMigration` already established toward `thecore_generators`: violation-detection logic lives in exactly one place (Ruby) instead of two that can drift apart.

`--json` is opt-in — a bare `rails thecore:check_practices` prints human-readable text grouped by file (the terminal-facing equivalent of `checkPractices.js`'s own emoji-prefixed log lines), matching the convention already set by RuboCop/RSpec, while `--json` is what CI and the extension actually consume. The task exits non-zero whenever violations remain unresolved after any `--fix` pass, so a CI pipeline can gate on it — the entire point of ADR 0002 calling it "usable in CI." A bare invocation scans the host app plus every ATOM under `vendor/submodules/` in one pass, the shape CI wants; `--atom=NAME` (the same flag Model/Migration already expose) narrows it to one ATOM, which is what the extension passes when the audit was triggered from a right-click on a single folder. `--fix` never asks its own confirmation — whoever passes it (a human, or the extension after its own QuickPick) has already made that call, and a second confirmation would make the flag useless from CI or any other non-interactive caller.

The Scaffold Files check (the `after_initialize.rb`/`assets.rb` marker validation) moves with this same work rather than waiting for the deferred ATOM generator, and is extended to the host-app context — today's JS only ever runs it in ATOM context, even though `addRootAction.js`/`addMemberAction.js` create and maintain both files in the host app too, so the app-context gap was never covered by anything. The ported Root/Member Action generator also drops the old JS behavior of writing locale entries into only `en.yml`/`it.yml`: it writes into every locale file already present in the target, the same set `check_practices` itself scans, so the generator's own output can never trip its own checker over a language the app already has beyond `en`/`it`.

The Model well-formedness check inside `check_practices` is rescoped to match ADR 0001's consequence. Since `Api::`/`RailsAdmin::` concern files are no longer generated by default, their plain absence is no longer a violation — it's the correct no-customization state. The check instead flags only inconsistent state: a model `include`-ing a concern module whose file doesn't exist, or a concern file present but missing its required marker. These are the cases that indicate a broken customization, not a correctly-defaulted model.

## Status
accepted

## Consequences
- Amends ADR 0002's phase grouping: Root/Member Action generators now ship alongside the leftover Phase 1 `check_practices` task, not bundled with the ATOM generator and App template. The ATOM generator, the App template, and Collection Action support all remain open, to be scoped in a later session.
- `check_practices`'s JSON shape becomes a real interface contract between `thecore_generators` and `thecore_code_extension` — changing it later is a breaking change for the extension, not a free internal refactor.
- On any app that has already adopted ADR 0001's defaults, the model-concern violation count drops to zero compared to today's JS audit. That's the fix working as intended, not a regression — worth calling out explicitly so it isn't mistaken for the audit silently losing coverage.

## Delivery tracking

This ADR's scope is now formally **Phase 2** (superseding ADR 0002's original Phase 2 grouping), broken into 8 tickets, all filed with the `ready-for-agent` label:

- Phase 2, `thecore_generators`: [#11](https://github.com/gabrieletassoni/thecore_generators/issues/11) Root Action generator → [#12](https://github.com/gabrieletassoni/thecore_generators/issues/12) Member Action generator (blocked by #11) · [#13](https://github.com/gabrieletassoni/thecore_generators/issues/13) check_practices Scaffold Files + Models + CLI skeleton (no blockers) → [#14](https://github.com/gabrieletassoni/thecore_generators/issues/14) check_practices Actions + `--fix` (blocked by #11, #12, #13) → [#15](https://github.com/gabrieletassoni/thecore_generators/issues/15) version sync + final docs (blocked by all others).
- Phase 2, `thecore_code_extension`: [#36](https://github.com/gabrieletassoni/thecore_code_extension/issues/36) delegate `addRootAction` (blocked by #11) · [#37](https://github.com/gabrieletassoni/thecore_code_extension/issues/37) delegate `addMemberAction` (blocked by #12) · [#38](https://github.com/gabrieletassoni/thecore_code_extension/issues/38) delegate `checkPractices` (blocked by #13, #14).
- Full spec: [thecore_generators#10](https://github.com/gabrieletassoni/thecore_generators/issues/10).

**Phase 3 (not yet scoped, deferred beyond this ADR):** the `thecore:atom` generator (porting `createATOM.js`), the `rails new -m` application template (porting `createApp.js`), and an actual Collection Action generator (today only *audited*, per #14, never generated). Resuming this initiative in a future session means picking up Phase 2's open tickets above first — none of Phase 3's scope should be started before Phase 2 lands, since Phase 3 would otherwise fork off an incomplete `thecore_generators` surface.

## Considered Options
- Keep `check_practices` scoped to Phase 1 only, defer Root/Member Action generators to Phase 2 as ADR 0002 originally grouped them — rejected: the two share enough surface (Action Companions) that building either without the other means re-deriving the "correct shape" twice.
- Plain-text-only output for `check_practices`, leaving the extension's own JS audit logic as a parallel implementation — rejected: two implementations of the same violation rules drift apart, as already evidenced by the model-concern check going stale against ADR 0001 without anyone noticing.
- Build Collection Action alongside Root/Member now, since ADR 0002 already names it — rejected: it has no prior implementation to port (unlike Root/Member, which have full JS parity today), and RailsAdmin's collection-action semantics are a genuinely different design problem, not a mechanical port.
