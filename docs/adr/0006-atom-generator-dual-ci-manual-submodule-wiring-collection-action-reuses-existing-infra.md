# ATOM generator (Phase 4) generates both CI files unconditionally and leaves git/submodule registration manual; Collection Action generator needs no new shared infrastructure

ADR 0004 deferred the `thecore:atom` generator and a Collection Action generator as part of Phase 3's block. ADR 0005 then scoped only the App application template out of that block, explicitly leaving both "deferred to a future session." This ADR resolves that remaining deferred block — referred to here as Phase 4, since "Phase 3" now refers specifically to the App template that already shipped. The spec is [thecore_generators#19](https://github.com/gabrieletassoni/thecore_generators/issues/19); delivery tickets are tracked below.

**Git hosting is generic; a private gem registry is not.** Every real ATOM in this codebase publishes to one of two places: RubyGems.org via a GitHub Actions workflow (the generic case — `model_driven_api`, `thecore_auth_commons`, `thecore_ui_rails_admin`, etc.), or a private gem host via GitLab CI (`mytask`, `thecore-spot-overrides` — Bancolini's own arrangement, not a general Thecore feature). Which *git host* a developer pushes an ATOM's repository to is an orthogonal, genuinely generic per-developer choice this ecosystem already treats as agnostic — nothing in `thecore_generators` should need to know or ask. `thecore:atom` therefore generates both `.github/workflows/gempush.yml` and `.gitlab-ci.yml` unconditionally, exactly matching `createATOM.js`'s existing (if slightly buggy) behavior, with no hosting-profile prompt. Two pre-existing bugs in the generated `gempush.yml` are fixed in the port: the `awk` pipeline computing the version string had a syntax error, and `env.version_exists` was referenced in `if:` conditions but never actually set — meaning the tag/publish steps have never functioned in any ATOM generated this way. `allowed_push_host` in the gemspec stays hardcoded to `https://rubygems.org`, matching every real generic ATOM already in this ecosystem — a private-registry-publishing ATOM (Bancolini's own "Spot" pattern) remains a manual post-generation customization, the same exclusion boundary ADR 0005 already drew for the App template's VPN/private-Gemfile-source/customer-submodule content.

**Git/submodule wiring stays a logged manual step.** Every real ATOM under `vendor/submodules/` in a host app is a genuine git submodule (confirmed via `.gitmodules`) — but `createATOM.js` itself never creates one; it only produces a git-uninitialized local directory (`rails plugin new -fG` explicitly skips git init). The Ruby port narrows that gap partially: it `git init`s the new ATOM directory with one initial commit of the generated tree, a safe and fully local action. It stops there — creating the remote repository and running `git submodule add` are logged as exact follow-up commands, worded generically (no GitHub- or GitLab-specific assumption), rather than automated. This mirrors how the Migration generator's own cross-ATOM/cross-app dependency wiring already handles the analogous case: log the exact step a human needs to take rather than performing an irreversible, credential-dependent action on their behalf.

**The ATOM `CLAUDE.md` skeleton extends the App template's existing fetch mechanism, rather than inventing a new one.** Every real ATOM in this codebase already carries its own `CLAUDE.md` (`mytask`, `thecore_backend_commons`, etc.), but `createATOM.js` generates none — only `rails plugin new`'s own boilerplate `README.rdoc`. This ADR adds a second sample file, `samples/ATOM_CLAUDE.md`, fetched via the same overridable-source-plus-raw-GitHub-URL-default mechanism the App template's own `rails new -m` script already implements for its devcontainer/CI/CLAUDE.md assets (an env var pointing at the assets' base location, defaulting to a raw GitHub URL on `thecore`'s `master` — see that script's own documentation for exact mechanics, not restated here) — a second consumer of an existing mechanism, not a new one. Its shape mirrors `samples/CLAUDE.md`: universal sections already filled in (the `mattpocock-skills` plugin mechanism and required skill sequence — relevant here because an ATOM is typically its own git repository a maintainer may open independently of any host app, the same reasoning `mytask`'s/`thecore_backend_commons`'s own `CLAUDE.md` already assumes — plus generic Rails-engine/gem testing conventions), with gem-specific sections (purpose, public API/concerns provided, models) left as clearly marked TODO placeholders.

**The Collection Action generator needs no new shared infrastructure.** Unlike Root/Member Action (which required extracting `ActionCompanion`/`CompanionFiles` as new shared modules when Root Action first shipped), the Collection Action generator is a pure third sibling: the same shared infrastructure already generalizes correctly once `action_kind "collection_action"` is declared (placement, pluralization, companion rendering, require-line/locale-entry logic all fall out for free). Its starter template mirrors Root Action's simplicity (`add_action "<name>", :base, :collection`, a minimal GET/JSON example with an `ActivityLogChannel` broadcast) rather than the more complex, hand-written `save_filters.rb`/`load_filters.rb` pattern already living in `thecore_ui_rails_admin` — a generator's starter template exists to be customized from a simple base, not to demonstrate every RailsAdmin `:collection` feature. `check_practices`'s fixable-violation delegation table — which has audited `lib/collection_actions/`/`config/collection_actions/` since the Actions check shipped (thecore_generators#14), always reporting `fixable: false` since no generator existed to delegate to — gains this generator as its missing entry, closing that gap.

## Status
accepted

## Consequences
- `thecore/samples/` now maintains two live dependencies fetched at generation time (the App template's devcontainer/CI/CLAUDE.md assets, and now `ATOM_CLAUDE.md` for the ATOM generator) — the same tradeoff ADR 0005 already accepted, extended to a second file.
- A freshly generated ATOM always carries one CI file that will never run (whichever host the developer doesn't end up pushing to) — the same "dead `gempush.yml` in `mytask`" wart already observed in real practice, accepted as the cost of staying git-hosting-agnostic rather than adding a prompt.
- Git submodule registration remains a two-step process: `git init` is automated, but remote creation and `git submodule add` are only ever logged. A new ATOM isn't a fully wired submodule of its host app until the developer runs those follow-up commands themselves.
- Neither the VS Code "Create an ATOM" command (`createATOM.js`) nor a Collection Action equivalent in the extension is touched by this ADR — `createATOM.js` keeps its current, fully JS-side implementation until a later, separate ticket delegates it to the new Ruby generator (mirroring the thecore_code_extension#36-38 delegation pattern).

## Considered Options
- Prompt for a hosting profile (generic GitHub+RubyGems vs private "Spot" GitLab+private gem host) — rejected: conflates two independent axes (git hosting, which is generic and per-developer; private gem registry, which is entirely Bancolini-specific) into one prompt. The generic gem should never encode Bancolini's own private-registry arrangement, matching the exact exclusion boundary ADR 0005 already drew for the App template.
- Only generate the CI file matching whichever host the developer says they'll use — rejected: would need the same rejected hosting-profile prompt just to decide file selection, adding interactive friction to avoid a cost (one unused, inert CI file) that isn't actually harmful.
- Have the generator create the remote repository and run `git submodule add` automatically — rejected: an irreversible, auth-dependent, cross-boundary action; matches this gem's existing convention (the Migration generator's cross-ATOM dependency wiring) of logging exactly what a human needs to run rather than performing it un-confirmed on their behalf.
- Have the Collection Action generator's starter template match the real hand-written `save_filters.rb`/`load_filters.rb` pattern (GET+POST, redirect, persistence) — rejected: that's a specific, non-generic business feature, not a good minimal starting point. Root Action's simpler GET/JSON/`ActionCable`-broadcast shape is already this gem's established "minimal working example" convention.
