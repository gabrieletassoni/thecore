# GitHub Actions CI sample and non-interactive App template close out ADR 0005's deferred items; createATOM.js/createApp.js delegate to their shipped generators; Headless CLI narrows to one surviving command

ADR 0005 shipped the App application template scoped to GitLab CI only, interactive-only, and explicitly tracked two items as future issues without filing them: "a GitHub Actions pipeline equivalent to the generic GitLab CI" and "an unattended/non-interactive invocation mode for the template." ADR 0006 (Phase 4) separately left two follow-ups unfiled: delegating `createATOM.js` to the new `thecore:atom` generator, and — discovered only once `createApp.js` itself was examined — the same delegation gap for `createApp.js`. A 2026-09-18 audit also surfaced a fully independent, dormant "Headless CLI" PRD (`thecore_code_extension#23`, filed before this whole re-engineering effort started) whose 8-subcommand scope turned out to be almost entirely superseded by the Rails-native generators this initiative already shipped. This ADR — referred to as **Phase 5** — resolves all of it in one pass. Delivery tickets: [thecore_code_extension#39](https://github.com/gabrieletassoni/thecore_code_extension/issues/39), [#40](https://github.com/gabrieletassoni/thecore_code_extension/issues/40), [#41](https://github.com/gabrieletassoni/thecore_code_extension/issues/41), [thecore#20](https://github.com/gabrieletassoni/thecore/issues/20), [thecore_generators#23](https://github.com/gabrieletassoni/thecore_generators/issues/23) — exact split/blocking edges finalized at `/to-tickets`.

**GitHub Actions CI sample: same git-hosting-agnostic reasoning as ADR 0006, extended to the App template.** ADR 0006 settled that git hosting is a generic, per-developer choice orthogonal to gem-registry/deploy-target concerns, and its own text already named "a Main App" alongside ATOMs when making that case. The same reasoning applies here without modification: `samples/.github/workflows/ci.yml` is added alongside the existing `samples/.gitlab-ci.yml`, and the App template fetches both unconditionally — no hosting-profile prompt, matching the ATOM generator's own precedent exactly. The new workflow mirrors the GitLab sample's stages (build/test/lint, gated the same way on `changes: [version]` and non-tag pushes) but resolves GitLab's `when: manual` (the production-deploy gate) differently: GitHub's closest equivalent, Environments with required reviewers, needs one-time human configuration in each repo's own Settings — not something a generated sample can be self-contained about. The prod-deploy job instead runs only on `workflow_dispatch` (manually triggered from the Actions UI), keeping the sample fully zero-config, in the same spirit as the GitLab sample's own "no-ops safely without `vendor/deploytargets`" design.

**Non-interactive App template mode: an explicit, fail-fast env var pair — no silent default.** Rails application templates cannot accept custom CLI flags the way `Thor::Group` generators can (`rails new` only recognizes its own built-in flags), so the trigger has to be an environment variable, following the existing `THECORE_SAMPLES_SOURCE` precedent already in `app_template.rb`: `THECORE_APP_TEMPLATE_NON_INTERACTIVE` (set/truthy = non-interactive). The template's one interactive decision point — the `yes?` prompt gating the devise/rails_admin/active_storage/etc. installer chain — needs its own explicit answer when unattended: `THECORE_APP_TEMPLATE_RUN_INSTALLERS=true/false`. Rather than silently defaulting either way, the template aborts with a clear message if non-interactive mode is on but this second variable isn't set, mirroring `thecore:atom`'s own `validate_non_interactive_options!` philosophy (ADR 0006) of never guessing at a required decision. This directly unblocks `createApp.js`'s delegation (see below): `createApp.js` today has zero interactive prompts and unconditionally installs the full gem set, so its delegated form always passes `THECORE_APP_TEMPLATE_RUN_INSTALLERS=true` — exact behavioral parity, no regression for existing VS Code users.

**`createATOM.js` and `createApp.js` delegate to their already-shipped generators — mechanical mirrors of `#36`/`#37`/`#38`.** Both commands keep their existing VS Code-side interactive flow (dialogs collecting the same inputs as today) and shell out instead of doing their own file placement. `createATOM.js` passes `--non-interactive --summary=... --description=... --author=... --email=... --url=... [--skip-api-admin-deps]` to `rails generate thecore:atom NAME` (flags already shipped in `thecore_generators` 3.10.0/3.11.0). `createApp.js` passes `THECORE_APP_TEMPLATE_NON_INTERACTIVE=1 THECORE_APP_TEMPLATE_RUN_INSTALLERS=true` to `rails new . -m <app_template.rb URL>` — which is why this ticket is blocked by the non-interactive mode landing first, not just conventionally sequenced after it.

**Headless CLI narrows to exactly one surviving command.** Of the original PRD's 8 target subcommands, 7 (`create-app`, `create-atom`, `add-model`, `add-migration`, `add-root-action`, `add-member-action`, `check-practices`) are already headless-scriptable via the Rails-native generators/rake task this whole initiative shipped — no CLI shim needed, and building one now would recreate exactly the JS/Ruby drift ADR 0002 set out to eliminate. Only `setup-dev-container` has no Rails boot to hook into and remains genuinely VS-Code-only. Its CLI shim is scoped to the 4 VS Code API points `setupDevContainer.js` actually touches (`showInputBox` via `CommandRunner.input`, `showErrorMessage`, `showInformationMessage`, `showWarningMessage`) rather than the original design's general 8-command shim surface, and still ships as a `bin` entry + `commander` subcommand in the existing package (not a separate package) — one subcommand today, room for more without a redesign if that's ever needed again.

## Status
accepted

## Consequences
- `app_template.rb` gains a second required-when-unattended env var (`THECORE_APP_TEMPLATE_RUN_INSTALLERS`) beyond the trigger itself (`THECORE_APP_TEMPLATE_NON_INTERACTIVE`) — two variables to document and get right, versus a single flag with a silent default, traded deliberately for never guessing at gem-installation behavior on someone's behalf.
- A freshly generated Main App (via the template) now always carries one CI file that will never run, exactly the same accepted wart ADR 0006 already introduced for ATOMs.
- GitHub-hosted Thecore apps get a weaker production-deploy story than GitLab-hosted ones out of the box (manual `workflow_dispatch` vs GitLab's richer environment-gated `when: manual`) until/unless a developer configures GitHub Environments themselves — an accepted asymmetry, not silently hidden.
- `thecore_code_extension`'s Headless CLI PRD (`#23`-`#31`) is closed as superseded rather than built as originally scoped; the `claude/grill-docs-cli-switches-pw8p7f` branch (an already-implemented multi-command shim for the old scope) and `claude/extract-createapp-templates-FB6x2` (an internal `createApp.js` refactor made moot by full delegation) are both deleted rather than merged.
- Once `#40`/`#41` ship, `createATOM.js`/`createApp.js` join `addModel.js`/`addMigration.js`/`addRootAction.js`/`addMemberAction.js`/`checkPractices.js` as thin wrappers — every dual-context VS Code command will delegate to `thecore_generators`, none will do its own file placement.

## Considered Options
- Require GitHub Environments + reviewers for the prod-deploy job, matching GitLab's `when: manual` as closely as possible — rejected: needs one-time manual repo configuration the generated sample can't perform itself, breaking the zero-config property every other generated asset in this initiative has had.
- Silently default the App template's installer-chain choice when non-interactive (e.g. always skip, safest) instead of requiring an explicit second env var — rejected: `createApp.js`'s existing behavior (always installs everything) would either regress silently or require a special-case override, and `thecore:atom`'s own precedent already established "fail loudly on an unspecified required decision" as this gem's convention.
- Build the full original Headless CLI (`#23`-`#31`) anyway, since a working implementation already existed on an unmerged branch — rejected: 7 of 8 subcommands would duplicate Rails-native functionality that already exists, reintroducing the exact drift-risk ADR 0002 was written to avoid; only the one genuinely uncovered command survives.
- Delegate `createApp.js` before the non-interactive mode exists, accepting a UX regression (a new prompt appearing where none did before) — rejected outright; sequencing the ticket after `#23` costs nothing and preserves parity.
